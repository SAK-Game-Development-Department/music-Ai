# musicai カテゴリC・D 実装指示書

対象リポジトリ: music-Ai（`musicai/` パッケージ）
対象範囲: 追加機能提案書のカテゴリ C（履歴・管理）と D（AI連携）のみ。基盤整備・他カテゴリは対象外。
最初の作業単位: **フェーズ F1（D2 → C1 → D3）**。F2・F3 は F1 完了後に別途指示する。

---

## 0. 進め方のルール（必ず守る）

1. **着手前に読む**：`CLAUDE.md`、`README.md`、`docs/`、`musicai/song.py`（曲ファイル形式の docstring）、`musicai/service.py`、`musicai/app.py`、`musicai/export.py`、`tests/` を読み、現状を把握してから計画を出す。読んでいないファイルについて推測で実装しない。
2. **計画を先に提示**：実装前に、変更するファイルと設計案を短くまとめて提示し、承認を得てから実装する。
3. **小さく進める**：機能（D2 → C1 → D3）ごとにブランチを分け、1機能 = 1 PR。
4. **既存挙動を壊さない**：`python -m unittest discover -s tests` が常に通る状態を保つ。既存の `check`（警告ゼロ・音符数＝モーラ数）は書き出し前の必須ゲートとして維持する。
5. **依存を増やさない**：アプリサーバーは標準ライブラリのみで動く構成。外部ライブラリを追加する場合は、理由と代替案（自前の軽量実装）を計画に書き、承認を得る。
6. **破壊的操作は単独で提示**：ファイル削除・履歴の書き換え・`git reset --hard` などは、他のコマンドと混ぜず、1つずつ承認を得る。
7. **日本語で説明**：変更の説明は日本語で、何をなぜ変えたかを短く添える。

## 1. 設計原則

- **ソースは git、生成物は git 外**：履歴管理の対象は YAML（`songs/`・`specs/`・`lyrics/`）だけ。MP3・MIDI・MusicXML は再生成できるので履歴に入れない（`.gitignore` で除外）。
- **git はユーザーに見せない**：UI・CLI の表示は「保存」「バージョン」「提案」の言葉だけを使う。コマンド名・ブランチ名・ハッシュを画面に出さない。
- **スキーマが契約**：人間・AI・CLI のすべてが、同じ JSON Schema を通った YAML だけを扱う。
- **提案と確定を分離**：AI の変更は「提案」として別に保持し、人間が採用したときだけ履歴に載せる。

## 2. F1 の作業

### D2：YAML スキーマ公開＋検証 API（工数 S）

**目的**：曲ファイルの形式を機械可読の契約にする。

**やること**
1. `musicai/song.py` の docstring を根拠に、曲ファイルの JSON Schema を `schemas/song.schema.json` として作る。`specs/` 用も同様に `schemas/spec.schema.json` を作る。
2. 曲・仕様ファイルに **`schema_version`（整数）を必須**にする。既存の `songs/*.yaml` と `specs/*.yaml` には、移行スクリプトで `schema_version: 1` を付ける。
3. 移行スクリプト `musicai/migrate.py` と、CLI サブコマンド `python -m musicai migrate` を作る。バージョンが上がるたびに変換関数を足せる構造にする。
4. 検証 API を `musicai/schema.py` に作る。入力は YAML ファイルのパス、出力は「合格／不合格」と、不合格の場合はエラー位置（キーのパス）と理由の一覧。CLI は `python -m musicai validate <path>`。
5. 既存の `check`（楽曲ルールの検証）とは役割を分け、`validate` は「ファイル構造の検証」とする。`check` の前に `validate` を呼ぶようにする。
6. CI（または `tests/`）で、`songs/` と `specs/` の全ファイルを検証するテストを追加する。

**検証方式の判断（計画で提案し、承認を得る）**
- 案A：`jsonschema` ライブラリを追加する。実装は短いが、依存が増える。
- 案B：標準ライブラリだけで、必要な範囲（型・必須キー・列挙）を自前で検証する。依存は増えないが、対応範囲が狭い。
- 標準ライブラリのみという制約を踏まえて、どちらを推すかを理由つきで書く。

**完了条件**
- 全 `songs/*.yaml`・`specs/*.yaml` が `validate` を通る（テストで確認）。
- `schema_version` が無いファイルは不合格になり、`migrate` で直る。
- スキーマ検証カバレッジ 100%。

### C1：履歴タイムライン＋歌詞 diff（工数 M）

**目的**：変更履歴を可視化し、歌詞の差分を行単位で見られるようにする。

**やること**
1. 履歴の単位を決める（計画で提案）。候補は「曲単位（`songs/<name>.yaml` ごと）」と「リポジトリ全体」。曲単位を推奨するが、実装コストと併せて判断する。
2. 履歴操作は `musicai/history.py` に集約する。git の呼び出しはこのモジュールだけに閉じ込め、他のモジュールは git を知らない。
3. 「保存」と「バージョン保存」を分ける。
   - 保存：作業中のファイルを上書きするだけ。履歴には載せない。
   - バージョン保存：メモ（任意）を付けて履歴に載せる。内部では git のコミットを使う。
4. API を追加する。
   - 履歴一覧（日時・メモ・変更概要）
   - 2つの版の歌詞 diff（行単位。追加・削除・変更を区別）
5. `musicai/web/` に履歴タイムラインを追加する。バージョンを時系列に並べ、2つ選ぶと歌詞 diff が行単位で表示される。表示に git 用語を使わない。
6. git が使えない環境（`git` 未インストール、リポジトリ外）でも、アプリが落ちずに「履歴機能は使えません」と表示して通常機能を続ける。

**完了条件**
- 2つの版の歌詞 diff が行単位で表示される。
- 画面と API のレスポンスに git 用語（commit・branch・hash）が出ない。
- `history.py` の単体テストがある（一時ディレクトリで git リポジトリを作って検証する）。

### D3：プロンプトテンプレート集（工数 S）

**目的**：AI が作曲・修正・レビューを、スキーマに沿って安定して行えるようにする。

**やること**
1. `prompts/` ディレクトリを作り、次の 3 種類のテンプレートを置く。
   - `compose.md`：テーマ・キー・テンポから `specs/xxx.yaml` を作らせる
   - `revise.md`：`songs/*.yaml` を、理論的な理由つきで修正させる
   - `review.md`：曲を理論・モーラ数・スキーマの観点でレビューさせる
2. 各テンプレートに、次を必ず含める。
   - 参照すべきスキーマ（`schemas/*.json`）と `schema_version`
   - 出力形式（YAML のみ。説明は別に分ける）
   - 書き出し前に `validate` と `check` を通すこと
   - 歌詞の読み指定（`{漢字|よみ}`）、melody 記法（`音名:拍数`、休符 `r`、メリスマ `~`、小節線 `|`）の規則
3. `CLAUDE.md` から `prompts/` を参照するように追記する。既存の手順は消さない。
4. スキーマ通過率を測る簡易スクリプト `scripts/measure_prompts.py` を作る。AI の出力 YAML を入力にして、`validate` の合格率を出す（AI の呼び出し自体は含めない）。

**完了条件**
- 3 種類のテンプレートが揃い、`CLAUDE.md` から辿れる。
- 目標：テンプレート利用時のスキーマ通過率 90%（測定手順を `docs/` に書く）。
